Lecture 3.1

Reproducible analysis pipelines for health research

Block 3 · Biostatistics core
The point

A reproducible analysis is one where anyone with the data can rebuild every number in the paper with one command, and get the same answer. That takes five habits: raw data that are never edited, code under version control with no patient data in it, recorded package versions, a pipeline that knows what is out of date, and a manuscript whose numbers come straight from code. Add a dated analysis plan and a data-access log, and a reviewer can trust your result. You will set all of this up for Project 3 before running a single model.

1. One project, one folder, raw data read-only

Keep each project in one self-contained folder where raw data go in untouched, and everything else is made by code.

What it is
A fixed layout: downloaded files in data-raw/, never edited; functions in R/; derived data and outputs written only by the pipeline; a README that says how to get the data and rebuild. Paths are relative to the project root, never C:/Users/me/….
Why it matters
If every derived file can be deleted and rebuilt, you can always answer “where did this number come from?”. If someone edited a file by hand, you cannot.
How to read it
Good: you can delete data/ and the outputs, run one command, and get them back. Bad: a file called final_v3_fixed.csv that nobody can regenerate.
What a change means
A correction to the data becomes a new raw file plus a line of code, never an edit. The history of what changed is then in the code.
project-3-nak/
├── data-raw/          # NHANES files as downloaded; read-only
├── data/              # derived data, written by the pipeline only
├── R/                 # functions: clean_nhanes(), fit_cox(), make_table1()
├── _targets.R         # the pipeline: which function makes which output
├── analysis-plan.md   # dated and frozen before outcome models are run
├── manuscript.qmd     # text, with numbers pulled from the pipeline
├── renv.lock          # exact package versions
└── README.md          # how to get the data and rebuild everything
Trap

Opening raw data in Excel “just to look”, then saving. Excel silently reformats: it has turned gene names such as SEPT2 into dates in published supplementary files, strips leading zeros from IDs, and reinterprets date formats. Treat raw files as read-only. Look at them in R.

Analogy

A kitchen with a recipe. You never alter the groceries; you change the recipe and cook again. Anyone with the same groceries and recipe gets the same dish.

2. Version control, and what never goes in it

Git records every change to your code; patient data, credentials and stored results must never enter it.

What it is
Git keeps a history of commits, each a snapshot of the code with a message saying why it changed. GitHub hosts a copy and adds review tools. A .gitignore file lists what git must never track.
Why it matters
You can see exactly which code produced the results you submitted, undo a bad change, and show reviewers the analysis evolved honestly. Tag the commit you submit (for example v1.0-submitted).
How to read it
Good: small commits with messages like “exclude pregnant participants, per plan section 3.2”. Bad: one commit called “stuff” the night before submission.
What a change means
Once a file is committed and pushed, assume it is public forever. Deleting it in a later commit leaves it in the history.
# .gitignore: never commit data, results or secrets
data-raw/
data/
_targets/        # the pipeline's stored results contain data
*.csv
*.rds
*.parquet
.Renviron        # API keys, database passwords
.Rhistory
.RData
Trap

“The repository is private, so the data are safe.” A private repository is still a copy on someone else’s server, one setting away from public, and copying credentialed data there can breach its data use agreement. Keep patient-level data out of git entirely, including the pipeline’s cache, plots of individual records and printed data frames in notebooks.

From your ML background

Same discipline as keeping training data and model weights out of a code repository. Track data versions by file hash instead: the pipeline below does this for you, as DVC does in Python projects.

3. Environments: record the package versions

An analysis depends on package versions as much as on code, so record them per project with renv.

What it is
renv gives each project its own package library and a lockfile, renv.lock, listing the exact version of every package and the R version used. The lockfile goes in git.
Why it matters
Packages change defaults. An update to a survey or imputation package can change a standard error or a pooled estimate without any change to your code. A lockfile lets you, a coauthor or a reviewer rebuild with the versions you used.
How to read it
renv::status() reports whether the library and the lockfile agree. If they do not, either snapshot (you meant to upgrade) or restore (you did not).
renv::init()       # once: a project library plus renv.lock
renv::snapshot()   # after installing or updating packages: record the versions
renv::restore()    # on a new machine: install exactly the recorded versions
Trap

Believing the lockfile freezes everything. It records the R version but does not install R, and it does not capture system libraries or the operating system. For full rebuilds years later, add a container image (for example a rocker image with the same R version). For a paper, renv plus a note of R version and platform is usually enough.

From your ML background

renv is the R equivalent of a virtual environment plus a lockfile (venv with poetry.lock, or a conda environment file).

4. Pipelines: let the computer track what is stale

A pipeline tool knows which outputs depend on which inputs, reruns only what a change invalidates, and refuses to let you report a stale result.

What it is
You declare each step as a target: an output, the function that makes it, and what it needs. The tool builds a dependency graph (a DAG). The idea comes from Make, which rebuilds a file when its inputs are newer; snakemake does the same for Python. The R package targets goes further and compares hashes of the data and the code, not timestamps.
Why it matters
Project 3 has slow steps: 20 imputations, then Cox and competing-risks models on each. Rerunning everything after a typo fix wastes an hour, so people stop rerunning and end up reporting results from old code. A pipeline makes the honest path the fast path.
How to read it
tar_outdated() lists what would rerun; tar_visnetwork() draws the graph with stale targets marked; tar_make() rebuilds them. “Everything up to date” means every output matches the current code and data.
What a change means
A change invalidates its target and everything downstream, and nothing else. A new data release reruns everything; a reworded paragraph reruns only the manuscript.
# _targets.R (shortened)
library(targets)
tar_option_set(packages = c("dplyr", "survey", "survival", "mice"))
tar_source()                                    # load the functions in R/
list(
  tar_target(urine_file, "data-raw/urine_na_k.xpt", format = "file"),  # hashed; demo_file, mort_file alike
  tar_target(clean,    clean_nhanes(urine_file, demo_file, mort_file)),
  tar_target(analysis, make_analysis_data(clean)),
  tar_target(imputed,  impute_nak(analysis, m = 20)),
  tar_target(fit_cox,  fit_cox_mi(imputed)),
  tar_target(table_hr, make_hr_table(fit_cox))
)

Each step is a function in R/, and each target names the function and its inputs. format = "file" makes targets hash the downloaded file, so a replaced file marks everything downstream as stale. The file names are placeholders; use the actual NHANES file names for your cycles.

What needs rerunning?

Click any box to “change” it (click again to undo) and watch which targets go stale, as tar_outdated() would report. Try the presets, then press Run tar_make() to bring everything up to date.

Trap

The run_all.R script, or worse, an interactive session with objects from last Tuesday. A table rendered from an object in memory may have come from code you have since changed. Two less obvious gaps: targets does not notice a package update unless you ask it to track that package (tar_option_set(imports = …)), and it cannot see files your functions read without declaring them.

From your ML background

This is the same idea as a DVC or Airflow pipeline, or a build cache: content-addressed outputs and a dependency graph. The difference is that targets tracks your R functions themselves, so editing a function invalidates exactly the targets that call it.

5. Literate reporting: numbers flow from code to manuscript

Every number in the paper should be computed where it appears, not typed in, so a reanalysis updates the text, the tables and the abstract together.

What it is
Quarto mixes prose with code chunks and renders to Word, PDF or HTML. Inline code drops a value into a sentence. Tables come from model objects via broom or gtsummary (Lecture 3.2).
Why it matters
Revisions change numbers. With hand-typed numbers, the abstract, the results and Table 2 drift apart, and reviewers notice. With computed numbers, they cannot.
How to read it
Good: you could search the manuscript source and find no hard-coded estimate. Acceptable: a Word draft for coauthors, generated from the Quarto source, never edited back by hand.
```{r}
hr <- targets::tar_read(table_hr)       # read the stored result, do not refit
```
Each unit higher Na/K ratio was associated with a hazard ratio of
`r fmt_hr(hr, "nak")` for cardiovascular death.

The chunk reads a finished result from the pipeline’s store; the inline expression formats it into the sentence (fmt_hr() is your own small helper). Rendering the manuscript can itself be the last target, so it goes stale when any result does.

Trap

Fitting models inside the manuscript file. Rendering then takes an hour, so you stop rendering, and the document falls behind the analysis. Fit in the pipeline; the manuscript only reads and formats.

Example · The reviewer round

Reviewer 2 asks you to exclude participants with chronic kidney disease. You add one line to make_analysis_data(), run tar_make(), and the pipeline reruns the imputation, the models, the tables and the manuscript. Every number in the response letter now matches the revised paper. Without a pipeline, this is a week of careful copying, with errors.

6. Seeds and code review

Random steps need fixed seeds so results repeat exactly; a second pair of eyes catches what reruns never will.

What it is
A seed fixes the random number stream used by multiple imputation, bootstraps, cross-validation and simulations. Code review means someone else reads your code against the analysis plan before results are final.
Why it matters
Without a seed, the same code gives slightly different estimates each run, and nobody can tell a bug from noise. Without review, a correct pipeline faithfully reproduces a wrong analysis.
How to read it
Changing the seed should move estimates only in the last decimal. If a conclusion flips with the seed, the Monte Carlo error is too big: use more imputations or more bootstrap replicates.
imp <- mice(analysis, m = 20, seed = 2026, printFlag = FALSE)  # the seed is part of the analysis

Pass the seed to the function that uses it, rather than one set.seed() at the top of a script; in a pipeline, targets also gives each target its own reproducible seed.

A reviewer of your code checks firstBecause
Every exclusion and derived variable matches the analysis planMost errors in health papers are in data preparation, not models
Survey codes for “refused” and “don’t know” (often 7/9, 77/99) are set to missingLeft in, they become extreme real values (Lecture 3.2)
Weights, strata and clusters are used in every estimate (Lecture 3.4)Ignoring the design gives wrong standard errors, and often wrong estimates
Trap

Trying seeds until the p-value drops under 0.05. It is a forking path like any other (Lecture 3.0, topic 9). Fix the seed in the analysis plan.

Analogy

Code review is the second screener from Project 2, applied to code. Independent checking catches what the first person cannot see.

7. Pre-registered analysis plans

Writing the analysis plan down, dated and frozen, before you look at the exposure–outcome results is what separates a test from a search.

What it is
A statistical analysis plan: the primary exposure and outcome definitions, the model, the covariates and why (from a DAG), the handling of missing data, survey design and competing risks, and the sensitivity analyses. Registered with a timestamp, for example on OSF Registries.
Why it matters
NHANES is public, so nobody can stop you peeking. The plan is your evidence that the main analysis was chosen before the answer was known. It also enforces the project rules: the reporting guideline (STROBE for Project 3) is followed from the protocol stage, not retrofitted.
How to read it
Feasibility counts before the plan are fine and required by the project rules (“data before design”): how many participants have urine sodium and potassium and linked mortality. Associations between exposure and outcome are not.
What a change means
Plans can change. Record each deviation in a table: what changed, when, why, and whether it was before or after seeing results. Report the planned analysis too.
Trap

“Pre-registration is for trials.” Observational analyses of public data have more freedom to fork, not less: many exposure codings, covariate sets and cycle groupings, each defensible. The plan is the cheapest insurance against the garden of forking paths.

Example · Project 3’s plan, in one line each

Exposure: spot-urine sodium-to-potassium ratio, continuous (spline) and in quartiles. Outcome: cardiovascular death from the linked mortality file, with non-cardiovascular death as a competing event. Design: survey weights, strata and PSUs. Missing covariates: multiple imputation, 20 datasets, seed fixed. Primary model and covariates justified by a DAG. Everything else is labelled sensitivity analysis.

8. Credentialed data, access logs and sharing code

For credentialed data such as MIMIC-IV, share the code and never the data; keep a log that shows you handled them as agreed.

What it is
PhysioNet credentialed access is personal: you complete training, sign a data use agreement for each dataset, and may not share the data or try to re-identify anyone. Derived datasets count as sensitive too; PhysioNet asks that they be shared only through PhysioNet under the same agreement.
Why it matters
A breach ends your access and can end a project, and it is a breach of trust with the patients whose records these are. Project 5A depends on MIMIC-IV, so the habits start now.
How to read it
A data-access log is one row per event: date, dataset and version, who accessed it, where it is stored, what was extracted, and when copies were deleted. A short log is enough; it answers an auditor’s or coauthor’s question in a minute.
Trap

Pasting MIMIC rows into an online chatbot to debug a query. PhysioNet’s 2025 guidance says credentialed data must not go to services that retain it, recommends locally run models, and says not to use a service whose data practices you cannot verify. Debug with the open MIMIC-IV demo subset, the schema, or made-up rows.

In the Gulf

Saudi Arabia’s Personal Data Protection Law came into force in September 2023, with full enforcement from September 2024, and treats health data as sensitive data with extra conditions on processing. When you later work with Saudi hospital or registry data, the same habits apply, with local law on top: data stay in approved storage, access is logged, and code is shared without data.

Sharing code with the paper. At submission (alongside the medRxiv preprint, project rule 5), make the repository public, tag the submitted version, and archive it on Zenodo, which issues a DOI for each GitHub release. Include a licence, the lockfile, and a README that says how to obtain the data. For NHANES, a script can download the public files; for MIMIC, the README points to PhysioNet and the reader gets their own access.

From your ML background

The release-with-a-DOI habit is the same as publishing model weights with a model card: someone else can run exactly what you ran, and cite it.

Check yourself

  1. You fix a bug in clean_nhanes() that affected only participants with missing potassium. Which outputs must be rebuilt, and is there anything to do besides running tar_make()?

    Show answer

    Everything downstream of the cleaned data: analysis dataset, imputations, models, tables, figures and manuscript. The pipeline finds these for you. Also record the fix in the commit message and, if results were already shared, tell coauthors which numbers moved and by how much.

  2. A coauthor emails you a corrected mortality-linkage file as an Excel attachment. What do you do with it?

    Show answer

    Save it unchanged as a new file in data-raw/, note where and when it came from, and point the pipeline at it (ideally after converting it to CSV with code, not by hand). Do not overwrite the old file or edit either one. The pipeline then marks everything downstream as stale.

  3. Changing the imputation seed moves your hazard ratio from 1.18 (95% CI 1.01–1.38) to 1.15 (0.99–1.34). What does that tell you, and what should you do?

    Show answer

    Monte Carlo error from too few imputations is large enough to matter near the threshold. Increase the number of imputations until the estimates are stable to the decimal you report. Do not pick the seed that gives the interval you prefer; the seed is fixed in the plan.

  4. After seeing results, you find that a spline for age fits much better than the linear term in your registered plan. Can you change it?

    Show answer

    Yes, as a documented deviation. Record what changed, when and why, note that it was made after seeing results, and report the planned analysis alongside. Reviewers accept honest deviations; they distrust silent ones.

  5. A colleague wants to put your Project 5A MIMIC extract in a private GitHub repository “so we can both work on it”. How do you respond?

    Show answer

    No. Each person needs their own PhysioNet credentialing and agreement, and the data should not leave approved storage. Share the code through git; each of you runs it against your own access. Log the decision.
